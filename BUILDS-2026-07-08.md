The FM synthesis port to the RSP (rsp_fm.S, commit b094ab6) is bit-exact —
two 300s dual-compute gates, 35840 + 34816 chunks, zero mismatches, and the

| Strategy | in-fight fps | why |
|---|---|---|
| ship all 4 channels, sync collect | 12.6 | CPU idles for the whole RSP compute ([RSPWAIT] fm≈2.4ms/chunk, q=0 — pure compute, not queueing) |
| + exact EG/quiet skip masks (re-gated, 0 mismatches) | 12.6 | fight channels keep their slots active; masks only prune idle slots |
| ship 2 / CPU 2 split | 21.8 | waits collapse (proving the overlap) but per-chunk glue (pack, cache ops, pm-index scans) exceeds the 2-channel saving |
| + cross-pump deferred collect (branch fm-defer-experiment) | 21.25 | samsho2's driver writes FM/ADPCM regs every tick; the sync hooks fire almost immediately (z80ms 329→502) |
| ADPCM-only + deferred collect | 20.25 | the defer machinery itself costs more than the ~0.5ms wait it hides |

Root cause: the C FM path on the VR4300 is very competitive (~1.1ms per
chunk per channel with the dcache-resident narrowed tables), and audio is
hard-real-time — RSP latency that the CPU cannot overlap is pure loss. The
FM ucode + verify infra stay in-tree (RSPFM=1 to enable, MVS64_RSPFM_SHIP
to set the CPU/RSP split); the deferral experiment lives on branch
fm-defer-experiment. A future design would need whole-pump batching with
RSP-resident state AND a driver-tolerant sync story to pay off.

**The deliverable remains the ADPCM-offload configuration below (26.3 fps
in-fight), rebuilt as `mvs64-samsho2-perf-fps-play4.z64` from the final
tree (identical hot path; FM compiled out by default).**

## Design (rsp_audio.S + ym2610.c `rspa_*` glue)

- **Monolithic command per chunk** (≤128 samples): DMAs in a param block +
  the jedi table + per-channel source slices, decodes all 7 ADPCM voices,
  DMAs out per-sample L/R contribution arrays + updated states + an
  end-of-block sequence word the CPU polls (uncached). No rspq saved state,
  so rsp_video commands interleave freely; issued on the **high-priority
  queue** so a long draw batch can't delay the audio pump.
- **The ADPCM source-address stream is deterministic** (independent of the
  decoded data), so the CPU stages exactly the bytes each channel will
  consume this chunk through the existing v.rom window caches. The ucode
  never touches the cart.
- **Pipelined**: the kick happens at the top of the synthesis chunk, so the
  RSP decodes underneath the CPU's FM/SSG passes (passes 0-2 never touch
  ADPCM state); pass 3 shrinks to leftovers + poll + adopt. Because audio
  synthesizes in real time, removing ~10% of wall from the critical path is
  amplified ~2x by the feedback equilibrium — hence +4.3 fps.
- **Bit-exact scalar port**: shift-add multiplies (the SU has no multiply);
  12-bit accumulator wrap, truncating divisions, clamps and the
  end-of-sample/end-stop semantics mirrored exactly. ADPCM-B chunks that
  could hit limit-wrap/repeat-restart fall back to the C decoder per chunk;
  a poll timeout falls back permanently (fail-safe, states untouched).
- `-DMVS64_RSPADPCM_VERIFY` dual-computes every chunk with the C decoders
  authoritative and `[RSPADPCM]` mismatch telemetry — this is the gate.

## Design (rsp_audio.S + ym2610.c `rspa_*` glue)

- **Monolithic command per chunk** (≤128 samples): DMAs in a param block +
  the jedi table + per-channel source slices, decodes all 7 ADPCM voices,
  DMAs out per-sample L/R contribution arrays + updated states + an
  end-of-block sequence word the CPU polls (uncached). No rspq saved state,
  so rsp_video commands interleave freely; issued on the **high-priority
  queue** so a long draw batch can't delay the audio pump.
- **The ADPCM source-address stream is deterministic** (independent of the
  decoded data), so the CPU stages exactly the bytes each channel will
  consume this chunk through the existing v.rom window caches. The ucode
  never touches the cart.
- **Pipelined**: the kick happens at the top of the synthesis chunk, so the
  RSP decodes underneath the CPU's FM/SSG passes (passes 0-2 never touch
  ADPCM state); pass 3 shrinks to leftovers + poll + adopt. Because audio
  synthesizes in real time, removing ~10% of wall from the critical path is
  amplified ~2x by the feedback equilibrium — hence +4.3 fps.
- **Bit-exact scalar port**: shift-add multiplies (the SU has no multiply);
  12-bit accumulator wrap, truncating divisions, clamps and the
  end-of-sample/end-stop semantics mirrored exactly. ADPCM-B chunks that
  could hit limit-wrap/repeat-restart fall back to the C decoder per chunk;
  a poll timeout falls back permanently (fail-safe, states untouched).
- `-DMVS64_RSPADPCM_VERIFY` dual-computes every chunk with the C decoders
  authoritative and `[RSPADPCM]` mismatch telemetry — this is the gate.
